# llmopenchat

Консольный чат и Telegram-бот для локальных GGUF-моделей и OpenAI-совместимых API. Клиент поддерживает потоковые ответы, историю диалогов, инструменты, поиск по документам и сценарии обработки текста.

Репозиторий содержит исходный код, скрипты запуска, тесты и примеры конфигурации. Веса моделей, серверные бинарники, окружения Python, личные настройки, токены, журналы и сохранённые диалоги устанавливаются или создаются отдельно.

## Возможности

- Локальные модели через управляемый сервер llama.cpp: Windows Vulkan, Linux CPU/Vulkan/CUDA; подключение к внешнему API и установленному vLLM на Linux.
- Каталог GGUF-моделей: загрузка выбранного квантования, проверка SHA256, переключение и удаление пакетов.
- Терминальный чат с горячими клавишами, сохранением и продолжением диалогов.
- Telegram-бот: общая сессия администратора и клиентов либо персональные диалоги; получение и отправка файлов, фото, видео и аудио.
- Режим юзербота через Telegram Business: модель отвечает собеседникам от имени подключённого аккаунта, с отдельной историей каждого чата.
- Веб, HTTP-запросы, чтение и запись файлов, ограниченный PowerShell — с подтверждением каждого вызова в чате.
- RAG: локальный поиск BM25 по текстам, исходникам, HTML, PDF и DOCX.
- Сценарии с проверкой JSON Schema: текст, stdin, файлы, отправка результата POST и входящий вебхук.
- Подготовка JSONL-датасетов и отдельный процесс LoRA/QLoRA-дообучения.

## Быстрый запуск на Linux

Клиент, Telegram-бот, инструменты файлов и PowerShell, RAG, сценарии, вебхуки и подготовка/запуск обучения поддерживают Linux. Для клиента нужен Python **3.10+**. Автоустановка llama.cpp поддерживает **x86_64 и ARM64** и использует официальные архивы Ubuntu с проверкой SHA256. Для x86_64 рекомендуется Ubuntu 22.04 или новее; ARM64-архивы собраны на Ubuntu 24.04 с GCC 14 и требуют соответствующей `libstdc++`. На другом дистрибутиве можно собрать llama.cpp самостоятельно и указать `server.executable` либо подключить внешний API.

Пример для Ubuntu/Debian, из каталога проекта, под обычным пользователем:

```sh
sudo apt-get update
sudo apt-get install -y python3 python3-venv python3-pip libgomp1 libcurl4 ca-certificates
sh Install.sh --model qwen3-0.6b
./Start-Chat.sh
```

`Install.sh` создаёт `.venv`, устанавливает клиентские зависимости, сервер и модель, записывает конфигурацию и делает скрипты запуска исполняемыми. Повторная установка продолжает скачивание. По умолчанию Linux использует **CPU**, поэтому GPU для запуска не требуется. Установка не выполняет системные команды от root. Выбор ускорения до установки модели:

```sh
# Vulkan: предварительно установите Vulkan loader и драйвер своей видеокарты.
LLMOPENCHAT_RUNTIME_BACKEND=vulkan sh Install.sh --model qwen3-0.6b
# NVIDIA: требуется драйвер, совместимый с выбранной версией CUDA.
LLMOPENCHAT_RUNTIME_BACKEND=cuda sh Install.sh --model qwen3-0.6b
```

Значения `LLMOPENCHAT_RUNTIME_BACKEND`: `cpu`, `vulkan`, `cuda`, `cuda13`. На x86_64 `cuda` выбирает CUDA 12.8, `cuda13` — CUDA 13.4; на ARM64 оба варианта используют CUDA 13.4. CUDA runtime скачивается вместе с сервером; драйвер устанавливается отдельно. Выбранный исполняемый файл сохраняется в `config.json`, поэтому при обычном запуске повторять переменную не нужно. Ошибки недостающих системных библиотек и драйверов видны в `.local/logs/server.log`.

Для внешнего API достаточно `sh Install.sh --client-only`: затем создайте `config.json` с `backend: "external"`, адресом и ID модели, как в разделе ниже. Ключ передаётся через `export LLMOPENCHAT_API_KEY='YOUR_API_KEY'`. Во всех примерах Windows ниже на Linux заменяйте `.\.venv\Scripts\python.exe` на `.venv/bin/python`, а пути — на Linux-пути. Все команды доступны также через скрипт:

```sh
./Start-Chat.sh doctor
./Start-Chat.sh ask "Привет"
./Start-Chat.sh rag add /srv/documents
./Start-Chat.sh chat --rag
./Start-Chat.sh scenario validate examples/scenarios/news/scenario.json
./Start-Telegram.sh
./Start-Telegram.sh --config profiles/bot.json --no-autostart
```

Интерактивный чат работает через SSH с терминалом; для фонового запуска используйте Telegram или `scenario serve`. В терминалах с программным управлением потоком Ctrl+S/Ctrl+Q могут перехватываться терминалом: выполните `stty -ixon` перед запуском или используйте `/save` и `/quit`.

Ограниченный PowerShell требует **PowerShell 7 (`pwsh`)**, установленный системным пакетом по [инструкции Microsoft](https://learn.microsoft.com/powershell/scripting/install/installing-powershell-on-linux), и `prlimit` из `util-linux`. Поддерживаются `/usr/bin/pwsh` и `/usr/local/bin/pwsh`; программа и её каталоги должны принадлежать root и быть недоступны для записи другим пользователям. Запускайте клиент от обычного пользователя: Linux не применяет лимит числа процессов к root. Как и в Windows, PowerShell выполняет только разрешённые вычисления и вывод в ограниченном runspace, после отдельного подтверждения. Для работы с файлами используйте файловые инструменты.

Для дообучения создайте отдельное Linux-окружение; установите подходящий PyTorch и `requirements-training.txt`. Для GPU нужны совместимые PyTorch/CUDA и оборудование. Команды клиента:

```sh
python3 -m venv .venv-sft
# После установки подходящего PyTorch:
.venv-sft/bin/python -m pip install -r requirements-training.txt
.venv/bin/python -m llmopenchat sft check --python .venv-sft/bin/python
.venv/bin/python -m llmopenchat sft train .local/sft/job/job.json --python .venv-sft/bin/python
```

### Фоновая служба на Linux

В [deploy/llmopenchat-telegram.service](deploy/llmopenchat-telegram.service) находится пример systemd для проекта в `/opt/llmopenchat`. Установите проект и модель в этом каталоге, создайте `config.json`, `credits.txt`, `whitelist.txt`, затем назначьте каталог отдельному пользователю службы. Пример после подготовки проекта:

```sh
sudo useradd --system --home-dir /opt/llmopenchat --shell /usr/sbin/nologin llmopenchat
sudo chown -R llmopenchat:llmopenchat /opt/llmopenchat
sudo chmod 600 /opt/llmopenchat/credits.txt /opt/llmopenchat/whitelist.txt
sudo cp /opt/llmopenchat/deploy/llmopenchat-telegram.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now llmopenchat-telegram
sudo journalctl -u llmopenchat-telegram -f
```

При другом каталоге или пользователе измените `WorkingDirectory`, `ExecStart`, `User` и `Group` в службе. Для GPU предоставьте пользователю службы доступ к устройствам драйвера; для `/dev/dri` обычно требуется членство в группах `render`/`video` вашего дистрибутива. Не предоставляйте посторонним процессам запись от имени пользователя службы: на Linux дескрипторы и проверки inode защищают файловые операции от подмены путей, но POSIX не запрещает другому процессу того же пользователя переименовывать файлы. Для переменных окружения можно создать `/etc/default/llmopenchat` с правами `600` и строками `ИМЯ=значение`; служба читает его при запуске.

Остановка через `systemctl stop llmopenchat-telegram` обрабатывается через SIGTERM: клиент закрывает бота и собственный сервер. При аварийном завершении Linux-клиента управляемый сервер и его дочерние процессы также завершаются; уже работавший внешний сервер остаётся под управлением его владельца. Для вебхука используйте отдельную копию службы с командой `.venv/bin/python -m llmopenchat --config ... scenario serve ПУТЬ` и задайте `LLMOPENCHAT_WEBHOOK_TOKEN` в окружении.

## Быстрый запуск в Windows

Нужен Python **3.10 или новее**; клиент проверяется на Python 3.12. Автоматический установщик локального сервера предназначен для Windows x64. Для Vulkan нужен совместимый видеодрайвер; объём RAM, VRAM и свободного диска зависит от выбранной модели.

Из каталога проекта запустите:

```powershell
.\Install.cmd --model qwen3-0.6b
.\Start-Chat.cmd
```

Первый скрипт создаёт `.venv`, устанавливает зависимости из `requirements.lock.txt`, **скачивает** сервер llama.cpp и выбранные веса, проверяет контрольные суммы и записывает `config.json`. Модель `qwen3-0.6b` — компактный вариант из встроенного каталога; для более сложных задач можно выбрать другую модель.

Без `--model` установщик скачивает Huihui GLM-4.7-Flash из источника по умолчанию. Для просмотра каталога после создания окружения:

```powershell
.\.venv\Scripts\python.exe -m llmopenchat models catalog
# Пример установки другой модели и квантования:
.\Install.cmd --model qwen3-4b-instruct-2507 --quant Q5_K_M
```

Повтор той же команды установки продолжает прерванное скачивание. При последующих запусках используются локальные файлы. Сервер запускается при входе в чат или запуске бота и останавливается при завершении клиента. Уже работающий совместимый API используется без его остановки.

## Подключение к внешнему API

Для внешнего сервера подготовьте только окружение Python:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock.txt
Copy-Item -LiteralPath config.example.json -Destination config.json
```

Измените в `config.json` следующие поля; остальные настройки можно оставить из примера:

```json
{
  "backend": "external",
  "base_url": "https://your-server.example/v1",
  "model": "your-model-id",
  "target_model": "your-model-id",
  "request_extra": {}
}
```

`model` должен совпадать с одним из ID в ответе сервера `/v1/models`. `target_model` используется как название источника в интерфейсе. Пустой `request_extra` убирает параметры шаблона, специфичные для локального профиля. Если API требует ключ, задайте его в окружении текущего PowerShell:

```powershell
$env:LLMOPENCHAT_API_KEY = "YOUR_API_KEY"
.\Start-Chat.cmd --config config.json chat
```

При `backend: "external"` скачивание весов и локального сервера не требуется. Пример отдельного профиля GLM-5.3 находится в `config.glm53.example.json`; адрес и ID модели в нём нужно заменить своими. Сообщения передаются выбранному серверу.

## Команды и настройки

Все примеры выполняются из каталога проекта:

```powershell
.\.venv\Scripts\python.exe -m llmopenchat                       # Главное меню
.\.venv\Scripts\python.exe -m llmopenchat chat                  # Сразу открыть чат
.\.venv\Scripts\python.exe -m llmopenchat ask "Привет"          # Один ответ и выход
.\.venv\Scripts\python.exe -m llmopenchat history               # История диалогов
.\.venv\Scripts\python.exe -m llmopenchat models                # Менеджер моделей
.\.venv\Scripts\python.exe -m llmopenchat doctor                # Диагностика установки
.\.venv\Scripts\python.exe -m llmopenchat --help                # Справка CLI
```

Глобальный `--config ПУТЬ` указывается **перед** командой. Например: `python -m llmopenchat --config config.json chat`. `Start-Chat.cmd` передаёт клиенту все аргументы. При активном `.venv` можно использовать `python` вместо полного пути к интерпретатору.

`chat` и `ask` принимают `--no-autostart`, `--max-tokens N`, `--show-reasoning` и `--rag`. `chat --session ПУТЬ` продолжает сохранённый диалог; `ask` историю сеанса не сохраняет. Подробные параметры: `python -m llmopenchat КОМАНДА --help`.

| Настройка `config.json` | Назначение |
| --- | --- |
| `backend`, `base_url`, `model` | Способ подключения, адрес API и ID модели |
| `temperature`, `max_tokens` | Вариативность и предел длины ответа |
| `system_prompt`, `show_reasoning` | Инструкция и отображение рассуждений |
| `request_timeout`, `request_extra` | Таймаут и дополнительные параметры запроса |
| `server.*` | Исполняемый файл, GGUF, размер контекста и параметры локального сервера |
| `rag.*` | Размер фрагментов и объём найденного контекста |
| `vision.*` | Передача изображений модели, размер и число изображений в истории |

Поля, отсутствующие в конфигурации, дополняются значениями из `llmopenchat/config.py`; путь к серверу по умолчанию выбирается для текущей платформы. Установщик записывает фактический путь к выбранной сборке. Объект `request_extra` заменяется целиком. Относительные пути сервера считаются от каталога проекта. После ручного изменения настроек перезапустите клиент.

Внутри чата `/help` показывает все команды. `F1` — справка, `F2` — главное меню, `F3` — инструменты, `Alt+Enter` — новая строка, `Ctrl+C` — отмена, `Ctrl+Q` — выход. `/save`, `/load` и `/history` управляют диалогами; `/thinking`, `/system` и `/clear` меняют состояние чата.

Веб, файлы, PowerShell и HTTP включаются независимо через `/tools` для текущего диалога. Перед каждым вызовом клиент показывает аргументы и запрашивает подтверждение. `/status` показывает состояние инструментов и RAG.

Для HTTP выберите пункт `6` в `/tools` (в Telegram — `/tools http on` или кнопка «Включить HTTP»). Репозиторий и PowerShell для этого не нужны. Затем можно попросить модель: «Отправь POST на https://httpbin.org/post, заголовок Content-Type: application/json, тело `{"message":"Привет"}` и покажи статус ответа». Модель должна поддерживать вызовы функций (`tool_calls`), а сервер — совместимый с OpenAI API режим инструментов. Клиент передаёт схему `http_request`, выполняет одобренный вызов и возвращает результат модели для продолжения ответа. Дополнительные пакеты для HTTP не нужны.

Аргументы `http_request` (обязателен `url`, по умолчанию `method: "GET"`):

```json
{
  "url": "https://httpbin.org/post",
  "method": "POST",
  "headers": {"Content-Type": "application/json"},
  "body": "{\"message\":\"Привет\"}"
}
```

Поддерживаются GET, HEAD, POST, PUT, PATCH, DELETE и OPTIONS, собственные заголовки и текстовое тело UTF-8 до 256 КиБ. GET и HEAD отправляются без тела. Допускаются до 32 заголовков общим объёмом до 16 КиБ. Ответ содержит `status_code`, `headers`, текстовое `body` и признак обрезки `truncated`; HTTP-ошибки 4xx/5xx также возвращаются модели. Чтение ответа ограничено 512 КиБ, тело для модели — 24 000 символов; бинарные и сжатые ответы не поддерживаются. Разрешены публичные HTTP(S)-адреса на стандартных портах 80/443; локальные и частные сети, данные доступа в URL и перенаправления заблокированы. Метод, URL, заголовки и тело видны перед подтверждением каждого запроса. `/tools off` в Telegram или пункт `4` в консольном меню отключают все инструменты. Новый консольный или личный Telegram-диалог сбрасывает доступы; в общем Telegram-чате настройки сохраняются администратором.

## Ответы по документам

Укажите путь к собственному документу или каталогу:

```powershell
.\.venv\Scripts\python.exe -m llmopenchat rag add "C:\Documents\notes.txt"
.\.venv\Scripts\python.exe -m llmopenchat rag list
.\.venv\Scripts\python.exe -m llmopenchat rag search "нужная тема"
.\.venv\Scripts\python.exe -m llmopenchat chat --rag
```

В чате доступны `/rag add ПУТЬ`, `/rag on`, `/rag off`, `/rag list`, `/rag search ЗАПРОС`, `/rag remove ID` и `/rag clear`. Поиск выполняется локально по словам, без отдельной embedding-модели. Сканированные PDF требуют внешнего OCR. Удаление документа из индекса сохраняет исходный файл.

## Сценарии обработки текста

Пример анализа новости находится в `examples/scenarios/news/`:

```powershell
.\.venv\Scripts\python.exe -m llmopenchat scenario validate examples/scenarios/news/scenario.json
.\.venv\Scripts\python.exe -m llmopenchat scenario run examples/scenarios/news/scenario.json --text "Текст новости"
.\.venv\Scripts\python.exe -m llmopenchat scenario init scenarios/my/scenario.json
```

Сценарий задаёт инструкцию, JSON Schema ответа, параметры генерации и способ выдачи результата. Вместо `--text` можно передать `--input-file ПУТЬ` или UTF-8 stdin. Сетевые адреса разрешаются списком origins в соседнем `hosts.txt`; пример по умолчанию запрещает сетевые действия. Разрешения инструментов сценария задаются его конфигурацией.

Для HTTP-запросов модели в сценарии задайте `"harness": {"http_enabled": true, "auto_approve": ["http_request"]}` и добавьте origin назначения в `hosts.txt`, например `https://httpbin.org`. Доступ к HTTP не зависит от `web_enabled`. В этом режиме вызовы заранее разрешены конфигурацией, без интерактивного подтверждения; общие ограничения HTTP сохраняются. Пустой `auto_approve` оставляет вызовы запрещёнными.

Для входящего вебхука установите `LLMOPENCHAT_WEBHOOK_TOKEN` и запустите `scenario serve ПУТЬ`. По умолчанию он слушает `127.0.0.1:8765` и принимает `POST /run` с JSON `{"text": "..."}` и Bearer-токеном. Дополнительные параметры доступны через `scenario serve --help`.

## Telegram-бот

Создайте в корне проекта два личных файла:

- `credits.txt` — только токен вашего бота, полученный у BotFather.
- `whitelist.txt` — разрешённые Telegram username через запятую, например `@alice, bob_user`. Символ `@` необязателен, регистр не учитывается.

В режиме администратор + клиенты `whitelist.txt` можно создать позже: без него доступен только администратор.

Запуск: `.\Start-Telegram.cmd` или `python -m llmopenchat telegram`. Другие пути можно передать флагами `--credits` и `--whitelist`; `--config` ставится перед `telegram`.

Для режима **администратор + клиенты с общей сессией** добавьте в `config.json`:

```json
{
  "telegram": {
    "admin_user_id": 123456789,
    "repository": "projects/shared-repo"
  }
}
```

Замените `123456789` на числовой Telegram user ID администратора: его можно узнать командой `/id` у бота. Роль закреплена за этим ID и не зависит от изменения username. Администратору доступ разрешён по ID; клиенты допускаются по username из `whitelist.txt`. Для одного запуска ID можно переопределить: `python -m llmopenchat telegram --admin-id 123456789`.

Все участники обращаются к одной выбранной модели в рамках одного общего диалога. Каждый следующий запрос использует общий контекст, включая сообщения и ответы другим клиентам. Запросы выполняются последовательно в порядке поступления; ответ получает чат, из которого поступил запрос. Клиентам доступны текстовые запросы, загрузка файлов и команды `/start`, `/menu`, `/help`, `/status`, `/id`.

Только администратор управляет моделью, системной инструкцией, инструментами, репозиторием, RAG и историей, сохраняет или загружает диалог, сбрасывает его и отменяет запросы. Клиенты могут передавать вложения в общий диалог; эти загрузки не меняют общий индекс RAG. Каждый вызов инструмента, в том числе вызванный запросом клиента, требует отдельного подтверждения администратора. Перед началом работы администратор должен открыть личный чат с ботом командой `/start`, чтобы получать эти подтверждения.

`telegram.repository` задаёт существующий общий каталог: абсолютный путь либо путь относительно корня проекта. Во время работы администратор может выбрать каталог через `/tools repo ПУТЬ`, затем включить инструменты через `/tools`. Без выбранного репозитория используется `.local/telegram/shared/workspace`. Настройки инструментов и выбранный каталог сохраняются в `.local/telegram/shared/settings.json`, текущий диалог — в `.local/telegram/shared/current.json`. При запуске непустой `telegram.repository` задаёт каталог заново; удалите этот параметр или укажите `null`, чтобы восстановить последний выбор. `/clear` начинает новый общий диалог, сохраняя репозиторий, инструменты и настройки RAG.

Без `telegram.admin_user_id` (либо с `null`) остаётся прежний режим: у каждого пользователя отдельные диалоги, рабочая папка и RAG, а модель и сервер общие. Документы добавляются в личную базу знаний, `/rag on` включает поиск, `/tools` управляет инструментами с подтверждением пользователя. Команды: `/help`, `/id`, `/history`, `/save`, `/load`, `/cancel`.

### Режим юзербота: ответы от бизнес-аккаунта

В этом режиме входящие личные сообщения людей подключённому аккаунту Telegram передаются модели, а её ответ отправляется от имени этого аккаунта. Используется официальный Bot API и тот же токен из `credits.txt`: вход по номеру телефона, код подтверждения и MTProto-сессия не нужны. По умолчанию режим выключен (`telegram.business_enabled: false`).

1. В [BotFather](https://t.me/BotFather) откройте настройки своего бота и включите бизнес-режим — Business Mode; в новых версиях он может называться Secretary Mode.
2. В настройках аккаунта Telegram откройте **Telegram Business → Чат-боты** (название раздела может отличаться), подключите бота, выберите доступные ему личные чаты и разрешите отправлять ответы.
3. Узнайте свой числовой Telegram user ID командой `/id` в личном чате с ботом. Укажите его как `telegram.admin_user_id` и включите режим в `config.json`:

```json
{
  "telegram": {
    "admin_user_id": 123456789,
    "business_enabled": true
  }
}
```

Запуск с этой конфигурацией: `python -m llmopenchat telegram`. Для одного запуска можно включить режим флагом и сразу указать владельца:

```powershell
python -m llmopenchat telegram --business --admin-id 123456789
```

`--userbot` — синоним `--business`; флаги действуют только на текущий запуск. Владелец подключённого аккаунта должен совпадать с `telegram.admin_user_id`: подключения других аккаунтов игнорируются. Собеседников бизнес-аккаунта добавлять в `whitelist.txt` не нужно, наличие username также не требуется. Список доступных чатов задаётся при подключении бота в Telegram. Обычный личный чат с ботом продолжает использовать прежние правила администратора и whitelist.

Новые бизнес-диалоги используют `system_prompt` из конфигурации. Запросы обрабатываются последовательно с чередованием собеседников; очередь ограничена 100 сообщениями на чат и 1000 ожидающими сообщениями всего. При переполнении сообщение пропускается, а причина записывается в журнал клиента.

История сохраняется отдельно для каждой пары `business_connection_id` и ID чата в `.local/telegram/business/`, в каталоге с хешем идентификатора подключения. Она восстанавливается после перезапуска и не смешивается с общей сессией администратора или другими собеседниками. Сообщения владельца аккаунта и ботов не запускают автоответ; отключение подключения или права отвечать прекращает обработку. Telegram разрешает отвечать в доступных личных чатах с входящими сообщениями за последние 24 часа. О подключениях и правах: [BusinessConnection](https://core.telegram.org/bots/api#businessconnection), [Business Bots](https://core.telegram.org/bots/features#business-bots).

`delivered.json` рядом с историей хранит ID последних 1000 сообщений, на которые успешно отправлен ответ, чтобы обычный перезапуск не приводил к повторным автоответам при повторной доставке обновлений Telegram. Очередь незавершённых запросов в файл не сохраняется.

Собеседникам передаются только итоговые ответы модели: инструменты, рассуждения и внутренние ошибки им недоступны. Текст со слешем, включая `/clear` и `/tools`, считается обычным сообщением модели и не выполняет команды управления. При включённом `vision.enabled` фотографии и изображения JPEG, PNG или WebP, отправленные как документы, передаются модели вместе с подписью; без подписи используется просьба описать изображение. Загрузка выполняется в очереди после проверки владельца подключения и права отвечать. Отключение подключения прекращает обработку, в том числе после загрузки изображения. При выключенном vision модель получает только текстовую отметку о недоступном содержимом. Видео, аудио и остальные вложения по-прежнему требуют текстового описания. Файловые инструменты ниже доступны в обычном чате с ботом.

### Файлы и медиа в Telegram

Бот принимает документы любых форматов, фото, видео, аудио, голосовые сообщения, анимации, видеосообщения и стикеры. Вложения сохраняются в рабочей папке текущей сессии; модель получает их имя, тип, размер и внутренний `file_id`. По умолчанию содержимое изображений модели недоступно; его передача включается через `vision.enabled`, как описано ниже. Распознавание аудио и видео не реализовано. В личном режиме вложения изолированы по пользователям; в общей сессии они доступны в общем контексте.

Подпись к вложению становится запросом модели. Без подписи бот подтверждает получение и сохраняет сведения о файле для следующего сообщения; при включённом vision изображения также запускают ответ модели. Поддерживаемые RAG документы, загруженные в личный чат или администратором общей сессии, также добавляются в базу знаний; поиск включается отдельно через `/rag on`. Ограничения форматов и размера индекса RAG сохраняются, даже если вложение допустимо для передачи.

Вложения из альбомов и файлы, пришедшие во время выполнения запроса, обрабатываются последовательно через очередь. `/cancel` и закрытие личного чата отменяют текущий запрос и очищают очередь ожидающих вложений.

Явные просьбы скачать или отправить файл, например «Пришли report.pdf», выполняются и при включённом RAG с пустой базой: для передачи файла поиск по содержимому документов не требуется.

Модель может вернуть вложение инструментом `telegram_send_file`: указать полученный `file_id` либо относительный `path` внутри выбранного репозитория. Для файлов репозитория включите `/tools code on`. По умолчанию файл отправляется как документ; `media_type` позволяет выбрать `photo`, `video`, `audio`, `voice`, `animation`, `video_note` или `sticker`. Поле `caption` задаёт подпись; видеосообщения и стикеры подпись не поддерживают. Получатель закреплён за запросом: модель не выбирает другой чат. Каждая отправка требует отдельного подтверждения, в общей сессии — администратора; файл получает инициатор запроса.

Чтобы получить бинарный файл по GET и переслать его пользователю, включите `/tools http on` и попросите, например: «Скачай https://example.com/report.pdf и пришли PDF сюда». Модель вызывает `http_download` с `url`, необязательными `headers` и `filename`, получает `file_id`, затем передаёт его в `telegram_send_file`. Скачивание и отправка подтверждаются отдельно. `http_request` остаётся инструментом для текстовых HTTP-ответов. Пример аргументов двух последовательных вызовов:

```json
{"url": "https://example.com/report.pdf", "filename": "report.pdf"}
```

```json
{"file_id": "ID_ИЗ_РЕЗУЛЬТАТА_СКАЧИВАНИЯ", "caption": "Отчёт", "media_type": "document"}
```

Загрузка входящего файла из Telegram ограничена 20 МиБ; `http_download` и исходящие файлы — 50 МиБ, отправка как `photo` — 10 МиБ. Для `http_download` действуют ограничения публичных HTTP(S)-адресов, стандартных портов и запрет перенаправлений из раздела HTTP выше.

### Ответы по изображениям

Для анализа фотографий нужна модель с поддержкой изображений и совместимый сервер. Сам флаг в клиенте не добавляет эту возможность текстовой модели. Включение в `config.json`:

```json
{
  "vision": {
    "enabled": true,
    "max_input_bytes": 10485760,
    "max_pixels": 24000000,
    "max_side": 1536,
    "max_image_bytes": 524288,
    "max_history_images": 4
  }
}
```

По умолчанию `enabled` равен `false`. Значения выше задают пределы: входящий файл до 10 МиБ и 24 мегапикселей, подготовленное изображение до 1536 пикселей по длинной стороне и 512 КиБ; в контексте остаются до четырёх последних изображений. Лимиты можно уменьшать. Принимаются JPEG, PNG и WebP; расширение или MIME-тип не заменяет проверку содержимого. Клиент исправляет ориентацию EXIF, уменьшает изображение и перекодирует его. Некорректные или слишком большие изображения не передаются модели; в бизнес-режиме собеседник получает просьбу прислать подходящее изображение или описание.

Запрос содержит текст и стандартную часть `image_url` с локально подготовленным изображением в base64; ссылки на загрузку Telegram и токен бота модели не передаются. Изображение отправляется выбранному в `base_url` серверу, поэтому для внешнего API это передача внешнему провайдеру. Совместимость формата описана в [OpenAI Images and vision](https://developers.openai.com/api/docs/guides/images-vision).

В сохранённых JSON-диалогах находятся подготовленные изображения в base64. Когда число изображений превышает `max_history_images`, старые изображения заменяются текстовой отметкой, а текст сообщений сохраняется. Изоляция личных и бизнес-диалогов действует и для изображений. При выключении vision изображения из прошлой истории не передаются текстовому серверу.

Для внешнего API выберите `backend: "external"`, укажите `base_url` и `model` сервера с поддержкой изображений, очистите специфичные для прежней модели параметры через `"request_extra": {}` и включите `vision.enabled`.

Обычный вопрос по изображению при выключенных инструментах передаётся без схем вызова функций. Для просьб переслать файл и явно включённых инструментов сохраняются прежние подтверждения; выбранная модель должна поддерживать и вызовы функций.

Для локального llama.cpp нужны совместимая vision-модель в GGUF, соответствующий ей мультимодальный проектор и сборка `llama-server` с поддержкой этой модели. Укажите GGUF в `server.model_path`, а проектор передайте через `server.extra_args`, например:

```json
{
  "vision": {"enabled": true},
  "request_extra": {},
  "server": {
    "model_path": "models/vision/model.gguf",
    "extra_args": ["--mmproj", "models/vision/mmproj.gguf"]
  }
}
```

Это пример путей: модель и проектор нужно подготовить отдельно и выбрать совместимую пару. Замените прежний список `extra_args` целиком, убрав `--chat-template-file` с шаблоном GLM; параметры и шаблон должны соответствовать выбранной vision-модели. Поддерживаемые модели и запуск с `--mmproj` описаны в [llama.cpp Multimodal](https://github.com/ggml-org/llama.cpp/blob/master/docs/multimodal.md). После изменения конфигурации перезапустите клиент.

## Подготовка данных и дообучение

Формат датасета показан в `examples/sft.example.jsonl`. Создайте свой файл и проверьте его:

```powershell
.\.venv\Scripts\python.exe -m llmopenchat sft init .local/sft/data.jsonl
.\.venv\Scripts\python.exe -m llmopenchat sft validate .local/sft/data.jsonl
```

Исправьте примеры и отметьте проверенные ответы `status: "approved"`. `sft prepare` включает в обучение только одобренные данные. Для него требуется явный `--base-model` — HF ID или каталог исходной модели Transformers. GGUF не подходит для исходного checkpoint обучения.

```powershell
.\.venv\Scripts\python.exe -m llmopenchat sft prepare .local/sft/data.jsonl --output .local/sft/job --base-model Qwen/Qwen3-0.6B
.\.venv\Scripts\python.exe -m llmopenchat sft check --python .venv-sft/Scripts/python.exe
.\.venv\Scripts\python.exe -m llmopenchat sft train .local/sft/job/job.json --python .venv-sft/Scripts/python.exe
```

Перед `check` и `train` создайте отдельное `.venv-sft` и установите подходящий PyTorch и зависимости из `requirements-training.txt`. Обучение может скачать исходный checkpoint; режим LoRA/QLoRA выбирается при `prepare`. `sft from-session` позволяет подготовить кандидатов из собственных будущих диалогов; они также требуют ручной проверки.

## Локальные данные и проверка

| Путь | Содержимое |
| --- | --- |
| `.venv/`, `.venv-sft/` | Окружения клиента и обучения |
| `models/` | Скачанные GGUF и сведения о загрузке |
| `.local/runtime/` | Установленный сервер llama.cpp |
| `.local/logs/` | Журналы сервера |
| `.local/sessions/`, `.local/input-history` | Диалоги и история терминального ввода |
| `.local/rag/` | Индекс документов |
| `.local/telegram/users/` | Данные пользователей Telegram |
| `.local/telegram/shared/` | Общая сессия, настройки, RAG и рабочая папка режима администратор + клиенты |
| `.local/telegram/business/` | Отдельные истории чатов подключённого бизнес-аккаунта |
| `.local/sft/` | Собственные датасеты и задания из примеров выше |
| `config.json`, `credits.txt`, `whitelist.txt` | Личные настройки и доступы |

Окружения, веса, `.local/` и личные файлы перечислены в `.gitignore` и не входят в исходную поставку. Диагностика: `python -m llmopenchat doctor`; журнал локального сервера — `.local/logs/server.log`.

Проверка клиента и управления процессами без загрузки модели:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

На Linux: `.venv/bin/python -m unittest discover -s tests -v`. В GitHub Actions предусмотрена матрица Ubuntu/Windows и Python 3.10/3.12; Linux-проверки включают файловые инструменты, подмену путей, завершение процессов и PowerShell при наличии системного `pwsh` и `prlimit`.
